# Owner-managed embed authorization with two-layer enforcement

Status: accepted

The chatbot widget renders only inside websites the Owner has allowed. The application owns an embed allowlist of at most 20 exact HTTPS origins stored as one settings row, seeded with `https://springfieldcollege.ca` while genuinely unconfigured; an owner save — including a deliberate emptying of the list — is real configuration that persists across restarts and upgrades. Development exceptions are fixed (`http://localhost:3000`, `http://127.0.0.1:3000`), automatic outside production only, and never stored, shown, or honored as production entries.

Enforcement is two independent layers:

1. **Pre-render eligibility.** The public loader asks `GET /api/v1/embed-eligibility` — one candidate parent origin in, one boolean out — before it touches the host page. A denial, a malformed or missing candidate, a network failure, or an unverifiable answer all leave the page untouched: no launcher, iframe, style, or visitor-facing error, and only a generic console diagnostic. The response is wildcard-CORS-safe because it carries no credentials and no data beyond the one-bit decision.
2. **Browser-enforced ancestors.** The widget frame response's `frame-ancestors` policy is computed per request (in `proxy.ts`, on the Node runtime) from the current allowlist — `'none'` when production's list is empty — replacing ticket 21's build-time header. A copied or modified loader that skips the eligibility call gains nothing: the browser itself refuses to frame the chat from an unauthorized parent. Production standalone navigation to the frame is refused the same way (a non-iframe `Sec-Fetch-Dest`, or none at all, is denied), while standalone development testing stays available.

Why a public JavaScript API key is not a security boundary: everything the browser executes is readable and copiable, so a key shipped in the loader is at best a rendering flag — an attacker can extract it, host their own page, and pass the same check. The trust decision must live server-side (the allowlist) and be enforced by a mechanism the host page cannot alter (response headers the browser applies to the frame). The key would also create a shared, unrenewable secret across every embedding website. The eligibility API is therefore deliberately secret-free; its only job is to avoid rendering widget chrome where it will be blocked anyway.

Consequences: allowlist saves reach newly loaded widgets immediately with no redeploy, while an already-open authorized chat finishes normally; the loader's "no API calls" property (embed pins) is narrowed to exactly one credential-free, boolean-only call; rate limiting on the eligibility endpoint follows the public-visitor pattern since callers are unauthenticated host pages. Production's policy supersedes ticket 21's header in one respect — the application's own origin is no longer implicitly an ancestor, so a production page on the chatbot origin must earn an allowlist entry like any other website. Refusing a missing `Sec-Fetch-Dest` means browsers without Fetch Metadata (Safari before 16.4) cannot embed in production; that is the fail-closed cost of the standalone refusal.
