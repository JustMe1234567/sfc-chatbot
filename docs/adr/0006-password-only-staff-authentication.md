# Password-only staff authentication with logged detection

Status: accepted

Staff sign-in is a single username + password stage, verified by hosted Supabase Auth. There is no second factor on any account, including owners: no enrollment page, no TOTP challenge, no authenticator reset surface, and no factor columns in the application's staff table. Ticket 81's controls — the login log, suspicious-login flagging, and the temporary IP block on unknown-username hammering — are the compensating controls, chosen deliberately by the project owner: detection after the fact replaces prevention at sign-in, trading a compromised password's single-factor exposure for visibility into every attempt.

This supersedes the mandatory-TOTP clause of ADR-0004 (staff passwords, sessions, and factors owned by Supabase Auth with enrollment forced before dashboard access). What ADR-0004 contributes beyond that clause stands: Supabase Auth still owns passwords and sessions, the application database still owns usernames, membership, status, and roles, synthetic internal email identifiers still satisfy the email/password interface, and owner-issued password resets still revoke every session. The revocation is the reset's, not the password's: a member's self-service password change from Settings revokes no sessions — the acting member stays signed in — because there the account holder is the actor, while a reset responds to suspected compromise on behalf of someone else (ticket 82 review amendment).

What was given up, stated plainly: a stolen or guessed password now signs in on the first try; before this decision the attacker also needed the staff member's authenticator. The enrollment, recovery, and reset surface the second factor demanded (an enforce-then-enroll flow, an owner reset action, a trusted-operator recovery command mode, and per-account factor bookkeeping) was itself a standing cost — every one of those paths is a way to lose access and a thing to maintain. Detection cannot un-disclose what a successful intruder reads; it shortens the window and names the attempt. The owner accepted that trade-off for this deployment's risk profile.

Consequences: an existing aal1 session stays valid across the deploy (no re-sign-in forced by the removal); provisioned accounts reach the dashboard with the password alone; every active staff member is transfer-eligible; the legacy Better Auth `twoFactor` table is unaffected (inert since ADR-0004's migration, handled by separate housekeeping); and any verified factors left in hosted Auth are removed by a one-time cleanup run (`scripts/remove-enrolled-factors.ts`) so no account is left half-enrolled. The human step that no code performs: staff members delete the stale Springfield entry from their authenticator apps.
