# Supabase Auth for hosted staff access

Status: accepted (the mandatory-TOTP clause superseded by ADR-0006; the "password reset … revokes every session" behavior below now applies to admin-issued resets only — a member's self-service password change revokes no sessions, per the ticket-82 review amendment recorded in ADR-0006; the application roles are Admin and Admissions Advisor since ticket 102, 2026-11-26, with every existing account migrated in place)

Supabase Auth owns staff passwords and sessions, while the application database owns usernames, staff membership, status, and the Admin / Admissions Advisor roles (owner/staff/editor before ticket 102). Admins exist only through the bootstrap command; admins create Admissions Advisor accounts with an initial password, and reset or disable them from the Staff accounts page. There is no public signup, invitation email, or email-based recovery. A password reset preserves the enrolled factor (removed entirely by ADR-0006) and revokes every session. Synthetic internal email identifiers satisfy Supabase Auth's email/password interface but are never shown or used for delivery.

This supersedes ADR-0001's Better Auth and fully offline login choice: localhost uses the dedicated hosted test project, protected requests verify both the current Supabase session and the linked active staff account, and visitor sessions remain separate. Chat escalation remains an in-dashboard sound/attention event rather than outbound email. The migration starts with fresh staff identities and configuration-only data transfer so the original database stays intact.
