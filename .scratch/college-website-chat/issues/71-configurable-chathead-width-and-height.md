# 71: Add configurable chathead width and height

**Status:** ready-for-human  
**Category:** enhancement  
**Priority:** P2  
**Related:** [70: Configurable chatbot and dashboard branding](70-configurable-chatbot-and-dashboard-branding.md)

## Current behavior

Ticket 70 makes the chathead background, icon size, and padding configurable. The launcher remains square because its outer size is derived from `icon size + (padding × 2)`. Staff cannot independently control the launcher width or height, and rectangular chatheads are not supported.

## Desired behavior

Add separate **Chathead width** and **Chathead height** controls to the Branding Settings chathead card. Each control accepts **44–96 px** through the existing accessible bounded slider/numeric-control pattern. New configurations and Reset use **64 px width** and **64 px height**.

Keep the existing icon-size and padding controls independent. A configuration is valid only when `icon size + (padding × 2)` fits within both the selected width and selected height. Block an invalid save without changing the stored configuration, and show clear feedback that states the minimum width and height required by the current icon-size and padding values.

Center the icon and close mark within square or rectangular launchers. Set the launcher corner radius to **25% of the smaller configured dimension**, preserving the current rounded-square proportion while allowing rectangular dimensions. Keep the existing automatic foreground contrast, accessible name, visible focus treatment, and keyboard/touch behavior.

Persist width and height with the existing database-backed chathead branding configuration for SQLite and Postgres. Extend the public branding response and widget handoff with only these safe numeric values. Missing, malformed, or out-of-range values fall back safely rather than breaking the launcher.

Use the configured height when positioning the opened chat frame above the launcher, and account for the configured width in horizontal launcher placement. The launcher and opened frame must remain usable without horizontal or vertical overflow on supported phone viewports.

For branding rows saved before this ticket, initialize width and height from the existing derived outer size (`icon size + (padding × 2)`) so deployed chatheads do not unexpectedly resize. This compatibility behavior is separate from Reset, which deliberately changes the dimensions to 64 × 64 px.

2026-11-12: IMPLEMENTED (`ready-for-human`).

**Domain** (`src/domain/branding.ts`): `ChatheadConfig` gains optional `width`/`height` (44–96 px integers when present — absent is valid, which is exactly what pre-71 rows look like), and `resolveChatheadConfig` now answers a fully resolved shape: dimensions default to the derived outer size (`iconSize + padding × 2`) when missing — so deployed chatheads keep their size — and a row whose dimensions cannot hold its icon and padding (a hand-edited row) falls back to the whole default configuration rather than rendering clipped. The save-time fit rule is `chatheadFitRequirement`, returning the required minimum square size so the refusal can state it. The default configuration is now 64 × 64 (with the unchanged 48 px icon and 4 px padding, which fits at 56 required), so Reset deliberately resizes a legacy chathead while a software upgrade does not.

**Routes**: the chathead PUT validates the fit after the shape check and refuses with `chathead_does_not_fit` and the computed minimum ("The icon and padding need at least 88 × 88 px. …") before anything is stored — the previous configuration survives, verified by test and cert. The public `/api/v1/branding` read carries `width` and `height` in place of ticket 70's derived `outerSize` — a contract evolution, not a pure extension, justified because the derived square is meaningless once dimensions are independent and the loader and v1.js deploy in lockstep (a stale cached loader degrades safely to its inline defaults).

**UI**: two new sliders (Chathead width, Chathead height) join the chathead card with the same 44–96 bounds, outputs, and preview; the preview renders the rectangle with its proportional radius and the client applies the same fit rule for immediate feedback (the server remains authoritative). Reset sets 64 × 64 without touching the icon, favicon, color, icon-size, or padding values.

**Widget**: the launcher's CSS rides `--sfcw-w`/`--sfcw-h` with 64 px inline fallbacks, `border-radius: calc(min(w, h) × .25)` preserves the 14/56 rounded-square proportion for rectangles, and the opened frame hangs `16px + height + 4px` above the bottom (the width accounts for placement by keeping the right edge viewport-anchored — at the 96 px maximum the launcher still sits fully on screen at 360 px, which the cert asserts). The frame forwards the resolved config to the loader through the existing origin-checked `sfcw:branding` postMessage; the loader keeps its no-API-call property.

**Certification** (the extended `cert70-branding.mjs` run against a production build on a scratch Postgres db): the fit-blocked save is refused with the 88 × 88 message and nothing stored changes; a rectangular 96 × 44 configuration saves and renders on the live demo page with an 11 px radius (25% of 44) and the frame hanging exactly 4 px above the launcher's top; at a 360 px viewport neither the widest launcher nor the open frame overflows.
