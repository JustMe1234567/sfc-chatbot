# 26: Put keyboard focus in the widget when it opens

**Status:** ready-for-human
**Priority:** P2 — a11y blocker for browser testing (spec story 3)
**Found by:** pre-testing audit 2026-10-30 (a11y pass; verified directly)

**What to build:** Opening the widget gives keyboard users no usable focus point. The inner `autofocus` runs while the iframe is `hidden` (`frame/page.tsx:294-296`; loader creates the frame `hidden` at `loader.ts:70`), so it never lands; the click handler's `frame.contentWindow?.focus()` (`loader.ts:117`) then falls through to the iframe's `<body>`. Keyboard users re-Tab from the top of the frame document on every open, from an unpredictable starting point.

- [ ] On open (after the frame is visible), focus lands on a deliberate target inside the frame — the close button or the composer — via a postMessage handshake or by having the frame app focus the target when it learns it became visible.
- [ ] Reopening the widget behaves identically (the target is refocused each open, not just on first load).
- [ ] Closing still returns focus to the launcher (existing behavior at `loader.ts:99` — keep it).
- [ ] Mouse users see no visible focus ring jump on open (use `:focus-visible` semantics — already the widget's pattern).
