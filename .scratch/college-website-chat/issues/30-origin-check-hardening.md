# 30: Origin-check hardening and recorded posture

**Status:** ready-for-human  
**Priority:** P3 — security hardening, queued (non-gating)  
**Found by:** pre-testing audit 2026-10-30 (security pass, line-cited)

**What to build:** Two origin-related gaps, plus one decision to record:

- [x] `sameOriginGuard` permits a missing `Origin` header (`src/api/staff.ts:78-82`). Browsers send Origin on cross-origin POSTs, so CSRF is covered in practice, but origin-absent requests (old browsers, some proxies) slip through. For cookie-authenticated mutations, require Origin **or** Referer to match, rejecting when neither is present. *(Audit premise corrected on implementation: the guard has rejected a missing Origin since ticket 03 — `origin && trusted.includes(origin)` falls through to the 403 when Origin is absent, so "rejecting when neither is present" already held and the audit's "slip through" reading was wrong. The real delta this box asked for was the Origin-or-Referer rule: the guard now accepts a Referer whose origin is trusted when Origin is absent, and still rejects an unsafe method with neither.)*
- [x] Public POSTs other than `/api/v1/presence` (create, messages, email, clear, return) have no origin check. They are bearer-token endpoints, so classic CSRF does not apply — but cross-site requests can still mint conversations or burn redemption attempts. Either add `sameOriginGuard` (the widget iframe's own fetches carry the chatbot origin) or record the decision that rate limiting is the only defense and why. *(Decision recorded: rate limiting is the defense; no guard added. Reasons in ticket 11's 2026-11-12 comment.)*
- [x] Whichever way the public-POST decision goes, it is written into ticket 11's comment (superseding the currently-wrong claim fixed in issue 23).

## Comments

2026-10-30: Filed from the audit. Non-gating: the practical CSRF surface is covered today; this closes edges and makes the posture explicit.

2026-11-12: Implemented. **Box 1:** `sameOriginGuard` (src/api/staff.ts) now implements Origin-or-Referer: a present Origin is the whole verdict (trusted → pass, untrusted → 403 `cross_origin_blocked`, unchanged); an absent Origin falls back to the Referer's origin (trusted → pass; untrusted or unparseable → 403); neither header → 403. Both headers are browser-set and unforgeable by cross-site script, so the security bar is unchanged — the fallback only admits the legitimate origin-less clients the ticket described. `git show a3b6329:src/api/staff.ts` confirms the audit's "permits a missing Origin" premise was already false when filed (missing Origin → 403 since ticket 03), so the reject-neither half needed no change — recorded above rather than silently re-ticked. Tests: new `tests/origin-guard.test.ts` (5): safe-method pass-through, trusted/untrusted Origin, trusted/untrusted/malformed Referer when Origin is absent, reject-neither with the stable code, and an integration pair on a real guarded route (cookie + Referer-only → 200; cookie + neither → 403; untrusted Origin beats a trusted Referer). **Box 2:** decision recorded rather than guards added — the public POSTs split into bearer-token endpoints (messages, clear, contact, return) whose credential never auto-attaches (CSRF cannot send it; "burning redemption attempts" requires already knowing the secret token, at which point the attacker needs no victim's browser), creation is inherently public and rate-limited per client key (platform-trusted headers per ticket 20, shared-store counting per ticket 24), and an Origin header is forgeable by exactly the non-browser attackers an origin check never stops — while the browser-borne cross-site paths it would stop are already rate-limited under the same key. Adding the guard would also hard-fail the direct-API seam the whole suite is built on for no material gain. The audit's list named the email route, which ticket 66 has since deleted. **Box 3:** the decision is written into ticket 11 — the security-review paragraph now states the posture as a decision with the date, and a dated comment records the full reasoning (superseding the issue-23 interim wording). Verified: typecheck clean; `tests/origin-guard.test.ts` 5/5; full SQLite suite green. No browser check needed (no rendering surface changed).
