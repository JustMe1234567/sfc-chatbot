# 93: Delta-based code-review reruns, anchored on a recorded last-reviewed SHA

Status: done

## What to build

Every `/code-review <fixed-point>` rerun re-scans the entire range even
when only one or two commits are new, because neither the review skill
nor the ticket records carry a "reviewed through" marker. Add a
convention that records the last-reviewed SHA in the ticket record — for
example a `Reviewed through: <sha>` line in each review or amendment
comment — and scope rerun sub-agents to the delta since that SHA, while
still cheaply re-verifying that recorded dispositions hold.

Triage decision (2026-11-20): **accepted, narrowed.** The convention
lives in two places, split by role. The **marker** is a tracker
convention: a `Reviewed through: <sha>` line in the review/amendment
comment of the ticket record, documented alongside the tracker's other
conventions in `docs/agents/issue-tracker.md`. The **consumption** lives
in the review skill itself — it spawns the sub-agents, so it scopes its
own reruns; invoker habit alone is what failed three times. The
"user-level skill shared across repos" option was misframed:
`.zcode/skills/` is repo-local and untracked — the tracked skill is
`.agents/skills/code-review/SKILL.md`, and its untracked `.zcode/`
mirror must be kept byte-identical (mirror consolidation is deferred
retro finding 6, not this ticket's job). A user-supplied fixed point
always governs the range start; the marker only narrows an
already-reviewed span.

## Acceptance criteria

- A review run that completes against a ticket record records
  `Reviewed through: <HEAD sha>` in that record, and the tracker
  conventions document the marker line.
- A rerun over a ticket record carrying the marker reviews only the
  commits after the marker SHA — with the same fresh-commit scrutiny
  today's runs give — plus a cheap re-verification that each disposition
  recorded since that marker still holds in the current code.
- The last-reviewed SHA is findable from the ticket record alone.
- With no marker, or a marker that does not resolve or is not an
  ancestor of HEAD, the review behaves exactly as today (full range)
  and states that the marker was ignored and why.

## Agent Brief

**Category:** enhancement
**Summary:** Record a `Reviewed through: <sha>` marker in the ticket
record after each review, and make rerun reviews scope themselves to
the delta since that marker plus a cheap disposition re-verification.

**Current behavior:**
Every `/code-review <fixed-point>` run reviews the entire
`<fixed-point>...HEAD` range, because neither the review skill nor any
ticket record carries a last-reviewed marker — so a rerun that reviews
a one-to-two-commit delta re-reads the same couple-hundred-file diff
and reproduces identical findings.

**Desired behavior:**
- After a review completes against a ticket record, the run records a
  `Reviewed through: <HEAD sha>` line in that record (in the review or
  amendment comment), and the tracker conventions document the marker.
- On a rerun over a ticket record carrying the marker, the review
  covers only commits after the marker SHA, at the same scrutiny as
  fresh commits, and additionally re-verifies — cheaply — that each
  disposition recorded since that marker still holds in the current
  code.
- With no marker, or a marker that does not resolve or is not an
  ancestor of HEAD, the review is exactly today's full-range behavior
  plus a stated note that the marker was ignored and why.
- A user-supplied fixed point always governs the range start; the
  marker only ever narrows an already-reviewed span.

**Key interfaces:**
- The tracker conventions doc (`docs/agents/issue-tracker.md`): gains
  the marker convention — what the line looks like and which comments
  carry it.
- The repo-tracked review skill (`.agents/skills/code-review/SKILL.md`):
  after pinning the fixed point and identifying the originating ticket
  record, read that record for the most recent marker; if present and
  valid, the sub-agent diff commands cover the delta since the marker
  and the aggregate step adds the disposition re-verification; when the
  run ends, record the new marker in the ticket record.
- The skill's untracked `.zcode/` mirror must end byte-identical to the
  tracked copy (the mirror-consolidation decision is deferred
  elsewhere; only parity is this ticket's job).

**Acceptance criteria:**
- [x] The tracker conventions document the `Reviewed through: <sha>`
      marker line.
- [x] A review run that completes against a ticket record leaves the
      marker recorded in that record.
- [x] A rerun over a marked record reviews only commits after the
      marker, with fresh-commit scrutiny, plus a disposition
      re-verification pass.
- [x] The last-reviewed SHA is findable from the ticket record alone.
- [x] A missing or invalid marker produces today's full-range behavior
      plus a stated ignore note.
- [x] The tracked skill and its `.zcode/` mirror are identical after
      the change.

**Out of scope:**
- Consolidating or otherwise resolving the `.zcode/skills/` /
  `.agents/skills/` mirror question (deferred retro finding 6 — only
  keep the two copies of this one skill identical).
- Changing the two-axis (Standards/Spec) separation or aggregation.
- Any application code, tests, or scripts — process/convention only.
- Instrumentation to measure review token spend.
