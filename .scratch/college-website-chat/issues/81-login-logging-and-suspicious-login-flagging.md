# 81: Login logging, suspicious-login flagging, and an owner-only Logs tab

Status: ready-for-human

## What to build

Make dashboard sign-ins observable: every attempt is logged, patterns are flagged as suspicious, and unknown-username hammering earns a temporary IP block. All of it is visible only to the owner. This is the replacement control for ticket 82's MFA removal, and it lands first — there is never a window with neither control.

- **Log every sign-in attempt** (success, failure, blocked) at the one credential path (`sign-in/username` in `src/auth/supabase-provider.ts`): attempted username, outcome, failure reason (unknown username, bad password, disabled account, blocked, …), client IP (the ticket-20 trusted-header derivation — `x-vercel-forwarded-for`/`x-real-ip` in prod, first `x-forwarded-for` entry in dev), user agent (captured nowhere today), and timestamp. New `login_events` table with SQLite + Postgres migrations in both dialects.
- **IP block**: failed attempts with a **non-staff username** from one IP, counted in a rolling 10-minute window; the 10th blocks that IP for **1 hour**. While blocked, non-staff-username attempts from that IP are rejected and logged with outcome "blocked". Attempts with a **valid** username are processed normally even from a blocked IP — correct password signs in, wrong password is an ordinary logged failure. Valid-username failures never trigger or extend a block. No manual unblock: the 1-hour auto-expiry is the only release. Blocked attempts still land in the log.
- **Suspicious flagging** — detection only (never blocks, no sound, no auto-lock), evaluated as each event is written. Defaults, adjustable at review:
  - (a) ≥ 5 failed attempts against one **valid** username from one IP within 10 minutes — the 5th and later events are flagged;
  - (b) a **successful** sign-in from an IP that account has never successfully signed in from before — flagged (baseline = prior successful events, so owners clearing logs reset the baseline; accepted at grilling);
  - (c) ≥ 3 failed attempts against **unknown or disabled** usernames from one IP within 10 minutes — the 3rd and later events are flagged (the IP block takes over at 10).
- **Owner-only Logs tab**: a new dashboard nav item named **Logs** with a hand-plotted scroll-or-paper SVG in the `Mark` idiom (ticket-72 precedent). Owners only — the app's single elevated role; staff and editors get no nav item, the page refuses them, and the API refuses them (the ticket-76 owner double gate: role check on the page, `requireStaff(request.headers, { roles: ["owner"] })` on every route). Second and third owners need nothing new: `bootstrap-owner` already creates multiple owners, and no "admin" role is added.
- **Two views** on the tab: **Log in logs** (the complete attempt log, flagged rows visually marked) and **Suspicious logs** (the flagged subset).
- **Deletion**: delete a single entry, delete checkbox-selected entries, and clear-all — each behind a confirm dialog (existing confirm patterns). Deletions themselves are not tracked anywhere.
- **Retention**: owner-configurable setting, default 90 days, mirroring the transcript-retention pattern (owner settings card + the daily maintenance cron prunes expired events and reports the count).
- **Fake/provider parity**: the test fake has always simulated a per-IP 10-failure→429 sign-in limit the real provider never had (`tests/auth-helpers.ts:43-44`, `tests/fake-auth-provider.ts:147-154`). The real rule above replaces it; the fake is aligned to the real semantics.

## Acceptance criteria

- Every sign-in attempt — success, failure, blocked — appears in the log with attempted username, outcome, reason, IP, user agent, and timestamp.
- After 10 non-staff-username failures from one IP within a rolling 10 minutes, that IP's non-staff-username sign-ins are rejected for 1 hour and logged as "blocked"; a valid username with the correct password still signs in from the blocked IP mid-block; the block expires automatically with no manual release.
- Criteria (a), (b), (c) flag events at the stated defaults; flagged events appear in the Suspicious logs view and are marked in the complete log.
- The Logs tab is reachable only by owners: no nav item for staff/editors, page and API requests refused by the owner gate on both layers.
- Single-entry delete, checkbox multi-delete, and clear-all each work behind a confirm dialog; deleted entries are gone.
- The retention setting (default 90 days) prunes old events in the daily maintenance pass.
- Tests cover store parity (both dialects), each flag criterion and its boundary, the block rule (threshold, window, expiry, valid-username carve-out), owner-only API gating, and the deletion actions; a cert script screenshots the Logs tab's two views, flag marking, and delete confirmations. Owner-UI cert RUNS need the hosted test project substrate (ticket 80's open decision gates the run, not the script).
- `GLOSSARY.md` gains **Login log**, **Suspicious login**, and **IP block** entries (written at filing time; land with this ticket's commit).

2026-11-19: **Review amendment — make login thresholds concurrency-safe.** The current threshold path performs count, event insertion, and IP-block upsert as separate operations. Concurrent failures can observe the same prior count, causing the fifth/third suspicious boundary or tenth-attempt block boundary to be missed. This violates the store's transaction/guarded-write invariant in ADR-0003 and weakens ticket 81's compensating control.

Acceptance criteria for this amendment:

- Evaluating a failed attempt, inserting its login event, and creating or extending any threshold-triggered block are atomic for the relevant IP/username decision.
- Concurrent non-staff-username failures cannot pass the tenth-attempt boundary without creating the one-hour IP block.
- Concurrent failures cannot silently miss the specified suspicious-event boundaries.
- A deterministic regression test exercises concurrent attempts against the real login-log/store seam and runs for both supported database dialects where the existing suite provides parity.
- The valid-username carve-out, generic failure response, rolling windows, expiry behavior, and adjustable threshold constants remain unchanged.

2026-11-19: Amendment implemented. `AppDatabase` gained a keyed `transaction` primitive (`src/db/appDatabase.ts`): Postgres opens a real `sql.begin` whose first statement takes a transaction-scoped `pg_advisory_xact_lock(hashtext(key))`, so same-key decisions serialize before any of their statements run — under READ COMMITTED two transactions could otherwise both count the same committed past and both miss. SQLite serializes on an in-process promise queue and deliberately takes no db-level BEGIN: one held open across awaits would collide with the store's own synchronous BEGIN/COMMIT blocks (nested BEGIN throws in whichever direction collides) and a rollback could undo a foreign statement interleaved into it; the queue gives the decision atomicity among keyed writers, and per-statement commit is the exposure this path always had (no crash-atomicity change). `recordLoginFailure` now evaluates (a)/(c)/block counts, inserts the event, and upserts any triggered block inside one transaction keyed `login-ip:<ip>` — the valid-username (a) decisions share the IP's queue, which over-serializes only and keeps every count exact. Carve-out, generic 401 body, windows, expiry, and constants untouched. Two deterministic regression tests appended to `tests/login-log.test.ts` fire exact-threshold concurrent attempts through the real seam with a fixed clock: 10 concurrent non-staff-username failures produce exactly 10 events, exactly 8 (c)-flagged (3rd–10th), exactly one `blocked: true` result, and a block that is live at the trigger instant and expired exactly one hour later; 5 concurrent valid-username failures produce exactly 5 events, exactly 1 (a)-flagged (the 5th), and no block — the carve-out under concurrency. Both were red against the pre-amendment code on SQLite (every concurrent count read 0 priors) and both pass with the fix on SQLite and Postgres; full suites green on both dialects (SQLite 566 pass/5 env-skips, Postgres 568 pass/3 skips — the restart-persistence file as always). Code review (both axes) fixed one interface-doc overpromise ("as one decision" → explicit same-key serialization wording). Declined with reasons: criterion (b)'s success path stays a bare count-then-write — the amendment scopes failures, and a concurrent first-success double-flag is over-flagging, which detection-only flagging tolerates; the provider's `isIpBlocked` pre-check racing a tenth failure can log an eleventh failure that re-stamps `blocked_until` from its own now — pre-existing landed behavior, the block is still created at the tenth, and "never extends" remains true for genuinely blocked attempts; the twin (c)/block count queries stay separate as previously recorded.

2026-11-19: **Second review amendment — close the active-block check race.** Human review rejected the disposition that allowed an attempt queued behind the threshold-setting attempt to remain a failure and re-stamp `blocked_until`. The pre-check in the provider occurs before the IP-keyed transaction, so it cannot determine the authoritative block state for a queued non-staff-username attempt. The active-block decision must be made inside the same keyed transaction that records the attempt.

Acceptance criteria for this amendment:

- A non-staff-username attempt re-checks the current IP block after acquiring the IP-keyed transaction/serialization boundary.
- If a live block exists at that point, the attempt is recorded with outcome `blocked` and does not run the ordinary failure-threshold path.
- A blocked or queued attempt never changes an existing block's `blocked_until`; the expiry remains exactly one hour from the threshold-setting attempt.
- An attempt queued behind the tenth failure is recorded as blocked rather than as an eleventh failure, without revealing the distinction in the generic client response.
- A deterministic concurrency regression test proves the queued-after-threshold case, the unchanged expiry, and the valid-username carve-out on both supported database dialects where the suite provides parity.
