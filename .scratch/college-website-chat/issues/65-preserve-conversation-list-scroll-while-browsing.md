# 65: Preserve each conversation list's scroll position while browsing

**Status:** ready-for-human
**Category:** bug
**Priority:** P2
**Related:** [12: Conversation desk](12-messenger-style-conversation-desk.md), [42: Loading feedback](42-consistent-loading-feedback-for-user-actions.md), [48: History route](48-history-tab-links-to-dead-route.md), [63: Bounded conversation desk](63-bound-conversation-desk-height-and-align-title.md)

## Agent Brief

**Summary:** Selecting a conversation near the bottom of the Conversations or History list must keep that list at the same position while the right-hand transcript changes. Conversations and History must remember their own positions when staff switch between the two tabs.

**Current behavior:** Selecting a row navigates to a conversation route that renders the desk again. The left list can jump to its top, so a staff member browsing lower rows loses their place and has to scroll back down for the next conversation. Frequent desk refreshes should not cause the same jump.

**Desired behavior:** While browsing within a tab, the list's scroll position and the clicked row stay in view when a conversation is selected; the right-hand conversation pane updates and the selected-row styling changes. The list, tab controls, and sound toggle do not visibly reset. Conversations and History each retain their own list scroll position for the current dashboard session, so switching away and back returns to the place staff were browsing. The existing list ordering, live updates, unread/attention changes, and route links remain functional.

**Key interfaces:** Preserve scroll state for the two desk list views across conversation-route navigation, tab switches, and server refreshes. Keep selection reflected in the URL so direct links, back/forward, and reloads still work. The bounded pane/layout work in ticket 63 may change list height but must not undo this behavior.

**Acceptance criteria:**

- [ ] With enough rows to scroll, select a conversation near the bottom of Conversations. Its row stays visible at the same list position and only the right-hand pane changes to the selected transcript; the list does not jump to its first row.
- [ ] Repeat the same interaction in History. Selecting several adjacent rows in either tab keeps staff in that part of the list, with a clear selected-row indicator and the existing row-level Loading feedback.
- [ ] Scroll Conversations, switch to History and scroll there, then switch back and forth. Each tab returns to its own prior list position during the current dashboard session.
- [ ] The one-second active-desk refresh and History refresh do not reset list position while browsing. A reply or read/attention update likewise does not send the list to the top. New data may still change the existing sort order; do not freeze or alter ordering to meet this ticket.
- [ ] Browser back/forward and direct conversation links still select the correct conversation. When a remembered position is beyond a shorter list after deletion or filtering by lifecycle, clamp to a valid position rather than showing an empty rail.
- [ ] Verify desktop and narrow-screen list/detail navigation with mouse, keyboard, and a long list. Scrolling the transcript remains independent of the list, and no horizontal overflow appears.

**Out of scope:** Changing which chats count as Active or History, list sorting, polling cadence, message contents, conversation permissions, sidebar expansion (ticket 64), or the visual redesign in ticket 63. Remembering list positions across a full browser restart is not required.
