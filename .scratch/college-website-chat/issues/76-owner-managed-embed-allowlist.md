# 76: Owner-managed embed allowlist

**Category:** enhancement
**Status:** ready-for-human

## Implementation record (2026-11-19)

- **Allowlist setting** (`src/settings.ts`, key `embed_allowlist`): one JSON row distinguishes never-configured from explicitly empty — an absent row seeds `https://springfieldcollege.ca` at boot (`seedEmbedAllowlist`, wired into both service builders), a saved `[]` persists and is never reseeded, and a corrupt or hand-edited row reads as invalid → enforcement fails closed to an empty list.
- **Domain rules** (`src/domain/embedAllowlist.ts`): the strict https-only origin normalizer (paths/queries/fragments dropped, credentials, wildcards, non-HTTPS and invalid URLs refused; non-default ports kept), the whole-list validator (≤ 20 exact origins, duplicates after normalization rejected with actionable messages), the eligibility decision (production = stored list only; outside production the trusted app origins and the two fixed loopback exceptions), the `frame-ancestors` resolver (production names the list exactly, `'none'` when empty), and the standalone-frame detector (production refuses any non-iframe `Sec-Fetch-Dest`, including none).
- **Public eligibility API** (`GET /api/v1/embed-eligibility`): rate-limited like other public endpoints, accepts `?origin=` and derives from `Origin`/`Referer` otherwise, answers `{allowed: boolean}` and nothing else with `Access-Control-Allow-Origin: *` + `no-store`; malformed/missing/unverifiable candidates read as denied with a 200.
- **Owner API** (`GET/PUT /api/staff/settings/embed-allowlist`): owner-only (`requireStaff` roles `["owner"]`), `sameOriginGuard` on PUT, full-list replace with the domain validator's actionable feedback.
- **Two-layer enforcement**: the loader (`src/widget/loader.ts` → rebuilt `public/widget/v1.js`) asks eligibility **before any DOM mutation** (dedupe marker on the script tag itself excepted) and leaves denied pages untouched with only the generic console diagnostic; the frame's `frame-ancestors` policy moved off the build-time header into `src/proxy.ts` (Node runtime), computed per request from the stored list, with `Cache-Control: private, no-store`; production standalone frame requests are refused with a bare 404 before rendering. `next.config.ts` no longer carries a static frame header (a second header would intersect).
- **Settings UI**: owner-only card on Settings (`embed-allowlist-settings.tsx`) — pasted-URL normalization on add, removable normalized-origin list, validation feedback, immediate PUT save per add/remove.
- **ADR**: `docs/adr/0005-owner-managed-embed-authorization.md`, including why a public JS API key is not a security boundary.
- **Loader fix the cert forced**: `document.currentScript` was read inside `boot()`, which is null when boot is deferred to `DOMContentLoaded` — the base then fell back to the host page's own origin, so a genuinely cross-origin embed (the production case) aimed the eligibility ask and the iframe at the *host*. The script element is now captured at script execution time. This was a latent pre-76 flaw the same-origin demo page could never expose; cert76 caught it.

## Agent Brief

**Category:** enhancement
**Summary:** Allow the chatbot widget to run only inside Owner-approved websites or the two fixed local-development origins.

**Current behavior:**
The versioned public loader renders its launcher and chatbot iframe on any page that includes it. The iframe has a static `frame-ancestors` policy derived from application configuration, but there is no Owner-managed list of host websites, no pre-render eligibility decision, and no production rule that refuses standalone frame use. Copying the loader can therefore render widget chrome on an unintended website even when the iframe is later blocked.

**Desired behavior:**
The application owns an **Embed allowlist**: at most 20 exact HTTPS website origins managed only by the existing Owner role. It starts with `https://springfieldcollege.ca` when genuinely unconfigured. An Owner may paste any URL from a website; the application normalizes it to its origin so every path on that origin may host the widget. The default is an ordinary removable entry, and once the setting has been explicitly saved, an intentionally empty list remains empty across restarts and upgrades.

Before adding any style, launcher, or iframe to a host page, the loader asks the chatbot server whether that page's origin is permitted. The public response exposes only an allow/deny result, never the complete allowlist. A refusal or any inability to establish authorization renders nothing. Independently, the iframe response applies a browser-enforced `frame-ancestors` policy based on the current allowlist so modified or copied loader code cannot bypass the decision. New loads see saved changes immediately; an already-open authorized chat may finish normally.

Production standalone access to the widget frame renders nothing. Outside production, `http://localhost:3000` and `http://127.0.0.1:3000` are automatic development-only exceptions and standalone frame access remains available for development. These local exceptions are not editable production entries.

**Key interfaces:**
- Embed allowlist setting: distinguishes never-configured from explicitly empty, seeds the Springfield College origin only in the former state, and returns normalized exact origins.
- Origin normalizer and validator: accepts a pasted HTTPS page URL, stores only its origin, rejects credentials and non-HTTPS production websites, removes duplicates after normalization, and enforces the 20-origin ceiling.
- Owner settings API: authenticated, same-origin guarded, Owner-only read/write access to the full allowlist; non-owners cannot read or mutate it.
- Public embed eligibility API: accepts or derives one candidate parent origin and returns only whether it is allowed; malformed, missing, unverifiable, or failed checks deny access.
- Widget loader boot contract: performs no DOM mutation until eligibility is confirmed and leaves no launcher, iframe, style, or visitor-facing error when denied.
- Widget frame authorization contract: applies the current allowlist as browser-enforced ancestor restrictions and refuses production standalone use independently of the loader.
- Settings UI: an Owner-only card on the existing Settings page with an Add website action, pasted-URL normalization, a removable normalized-origin list, and clear validation feedback.

**Acceptance criteria:**
- [ ] A genuinely unconfigured installation starts with exactly `https://springfieldcollege.ca`; an Owner may remove it, and a deliberately saved empty list is never reseeded.
- [ ] Pasting a URL such as `https://springfieldcollege.ca/programs/example/?campaign=fall` visibly normalizes and saves `https://springfieldcollege.ca`, authorizing every path on that origin.
- [ ] Production entries require exact HTTPS origins. Paths, queries, fragments, credentials, wildcard hosts, duplicates after normalization, invalid URLs, and a twenty-first distinct origin are rejected with actionable validation feedback.
- [ ] Only the Owner role can view or change the allowlist. Staff and editors receive the normal authorization refusal and do not see the management card.
- [ ] Saving an add or removal affects newly loaded widgets immediately without a build or deployment; already-open chats remain usable until their host page reloads.
- [ ] On an allowed production origin, the loader renders and the complete visitor chat journey continues to work.
- [ ] On an unauthorized origin, or when eligibility cannot be verified, the loader performs no DOM mutation and renders no launcher, iframe, style, or visitor-facing error. Any developer-console diagnostic is generic and does not disclose the allowlist.
- [ ] The public eligibility response contains only an allow/deny result and never returns the full allowlist.
- [ ] The widget frame independently carries a `frame-ancestors` policy reflecting the current production allowlist, so bypassing or modifying the public loader does not permit an unauthorized parent to frame the chat.
- [ ] Direct production navigation to the widget frame renders nothing, while standalone development testing remains available.
- [ ] Outside production, exactly `http://localhost:3000` and `http://127.0.0.1:3000` work automatically as parent origins; they are not stored or shown as Owner-managed entries and are unavailable as production exceptions.
- [ ] Automated coverage proves normalization and validation, unconfigured-versus-empty persistence, seed behavior on both supported databases, role authorization, boolean-only public responses, fail-closed loader behavior, dynamic ancestor enforcement, production standalone refusal, localhost development exceptions, and the unaffected authorized visitor journey.
- [ ] The embed-authorization decision and its two-layer enforcement are recorded in an ADR, including why a public JavaScript API key is not a security boundary.

**Out of scope:**
- Hiding, encrypting, or preventing download of the public widget JavaScript.
- Adding an API key or other reusable secret to browser-delivered code.
- Visitor accounts, visitor login, or restricting which people may chat on an approved website.
- Bot detection, CAPTCHA, Turnstile, or other direct-API abuse prevention.
- Changing the existing rate-limit policy or adding origin guards to unrelated public visitor APIs.
- Recording allowlist changes in the audit log.
- Wildcard domains, automatic trust of subdomains, or automatic trust of the `www` variant of an allowed origin.
