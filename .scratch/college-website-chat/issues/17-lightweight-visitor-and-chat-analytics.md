# 17: Add lightweight visitor and chat analytics to the staff dashboard

**Status:** ready-for-human

**What to build:** Add a small, staff-protected Analytics page showing live site visitors, total visitors, total chats, and a simple daily report. Use the existing chat data for conversation measures and a low-frequency, anonymous signal from the WordPress embed for site visitor measures. Keep the implementation suitable for the lightweight chatbot; this is not a full helpdesk analytics platform.

**Blocked by:** None. Coordinate the dashboard styling with ticket 13 and include the new analytics data in the Postgres schema/migration if ticket 11 lands first.

- [x] Define the numbers in the UI. **Live visitors** means distinct anonymous browsers with an active embedded page in the last 2 minutes, not just people who have opened or sent a chat. **Total visitors** means distinct anonymous browsers seen in the selected reporting period. **Total chats** means conversations created in that period, regardless of whether they were escalated. State that browser counts are estimates: one person across devices or cleared storage can count more than once, and script blockers can prevent counting.
- [x] Add an anonymous browser identifier for the embed, shared across tabs on the same site and lasting no longer than the chosen analytics retention period. Do not save an IP address anywhere in the application database, analytics tables, notification payloads, or dashboard; do not derive or display location or ISP from an IP address. Do not use email, chat credentials, message text, or staff identities as visitor identifiers. Send only the minimal signal needed for counting; validate its origin and rate-limit the public endpoint without persisting the IP. Document the site's privacy/consent implications before production use.
- [x] Send presence while an embedded page is visible, at a modest interval (about 30–60 seconds). Stop when the page is hidden or closed. An open but hidden chat iframe must not keep a browser falsely live. Reconcile this with the existing 3-second conversation polling and `visitor_last_seen_at`, which currently tracks chat return/email behavior; do not break live staff replies or visitor email decisions.
- [x] Show cards for live visitors, total visitors, total chats, and chats escalated. Offer Today, 7 days, and 30 days as reporting periods, using the site's configured reporting timezone (default Asia/Singapore) consistently for day boundaries. Live visitors is always a current snapshot; label it separately from period totals.
- [x] Show a simple daily table or chart for visitors, chats started, and escalations over the selected period. Add median first staff reply time only if the underlying message timestamps can support an accurate calculation; omit or clearly mark unavailable where there were no staff replies. Do not mine free-text transcripts for topics.
- [x] Compute aggregate reports on the server and protect analytics routes with staff authentication; owner-only access is acceptable if that matches the dashboard's permission model. Avoid loading full transcripts or sending individual visitor identifiers to the browser. Use indexed/aggregate queries or compact rollups so dashboard load does not scan every message on each refresh.
- [x] Define analytics data retention separately from transcript retention. Purging a transcript must not accidentally change previously reported aggregate chat totals; visitor identifiers should expire after the defined analytics window. Explain in the dashboard or documentation when historical data is unavailable.
- [x] Verify multi-tab deduplication, a hidden/closed page dropping from live after 2 minutes, period boundaries, empty-state and no-data reporting, chats without escalation, authentication, and reasonable request/write volume. Check desktop and narrow dashboard layouts. Run relevant tests and include screenshots or a short report in Comments when implemented.

## Context

The current widget creates a conversation only when a visitor first sends a message. Therefore, conversation rows can supply chat totals but cannot measure everyone viewing a page with the embed. Its iframe is created on page load and remains mounted when the chat is closed; an existing conversation is polled every 3 seconds and each authorized read refreshes `visitor_last_seen_at`. That signal is for chat presence and would miscount live site visitors. The dashboard currently has no visitor analytics page. This ticket follows the user's request for live visitors, total visitors, total chats, and simple reporting without adding a third-party analytics platform.

2026-10-28: IMPLEMENTED (`ready-for-human`).

**Data model** (migration `0013_analytics.sql`): `analytics_seen` — one row per anonymous browser per reporting day (`visitor_hash`, `day` PK, `first_seen_at`, `last_seen_at`; indexes on `day` and `last_seen_at`); `analytics_daily` — per-day chat/escalation rollups, deliberately unconnected to `conversations` so the transcript purge (ticket 10) can never move reported totals (regression-tested).

**Presence**: `POST /api/v1/presence` (public, origin-guarded like every unsafe route, in-memory rate limit 240/min/IP — the address is never persisted) takes a client-generated UUID, stores only its SHA-256, buckets it into the reporting day, and answers with the analytics retention period so the widget rotates its identifier on schedule. The iframe beats every 45 s while the host page is visible (`document.visibilityState` mirrors the top page even for the mounted-but-hidden frame) and stops instantly on hide; a browser drops from live after 2 minutes (`ANALYTICS_LIVE_WINDOW_MS` env for deterministic tests). `visitor_last_seen_at` and the 3 s poll are untouched — credential presence still governs return-email decisions. Browser id lives in the widget's localStorage on the chatbot origin (shared across tabs), rotates at creation + retention days, and a server-reported shorter retention only ever shortens it (a longer one never extends it). Multi-tab dedup and midnight cross-day live counting are unit-tested.

**Rollups**: every conversation creation counts a chat — the start route, and the clear route only when it minted the successor (`replaceConversation` now returns `{ successorId, created }`); the first `bot_active → awaiting_staff` transition in the messages route counts an escalation (releases never pass there).

**Report**: `GET /api/staff/analytics?period=today|7d|30d` (owner + staff, like the desk; editors 403) computes everything server-side from the aggregate queries — zero-filled daily table, period totals, live snapshot — and never ships transcripts or identifiers. Days are drawn in the owner-configured reporting zone (`GET/PUT /api/staff/settings/analytics`, default Asia/Singapore) via pure calendar math (DST-immune). Analytics expiry (`analytics_retention_days`, default 90, always on — corrupt/unset reads as default) rides staff desk traffic and the settings save, independent of transcript retention.

**UI**: `/dashboard/analytics` in the ticket-13 design system — four cards (live labelled "a snapshot, separate from the period totals"), period tabs, daily table, and footnotes: estimates caveat, retention window with the first unavailable day, and why median first-reply time is omitted (transcript purge would drift it — the ticket's own conditional). Owner gets the settings form on the page; staff see numbers read-only.

**Privacy documentation**: `docs/adr/0002-anonymous-presence-analytics.md` records what is stored (hashed random id, per-day presence, daily counts), what is never stored (IP anywhere, location/ISP, email/credentials/message text, visit histories), the consent posture (cookieless and anonymous, but a page-presence measurement the college's privacy notice should mention; blocking `/api/v1/presence` at the edge disables it harmlessly), and the rotation bound that stops an active browser becoming a long-lived tracker. GLOSSARY gained Analytics presence / Anonymous browser identifier / Reporting day / Analytics retention period, and Presence now disambiguates the credential-based signal.
