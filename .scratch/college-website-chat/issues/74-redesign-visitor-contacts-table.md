## Current behavior

The **Visitor contacts** page already lists only conversations whose visitor created a contact request. Each entry is a compact list row containing the visitor's name, email, phone, latest requested medium, and chat-start time, and the whole row links to the conversation. The page is restricted to owners and staff and paginates ten contacts at a time.

The page does not provide contact search or column sorting. Its metadata wraps into a single list-row line instead of the reference's scannable column layout. It also renders **Visitor contacts** once in the shared dashboard heading and again inside the page content.

## Desired behavior

Redesign only the right-side Visitor contacts content to follow the supplied reference's hierarchy and proportions while keeping the existing dashboard shell and design tokens:

1. Show one visible page heading in the content: the **FOLLOW-UP CONTACTS** eyebrow, **Visitor contacts** title, and the existing explanatory description. Suppress the shared header's duplicate visible title for this route only; keep its navigation, mobile Menu control, and accessible structure, and do not change other dashboard pages.
2. Place a contact-count pill below the introduction and a labeled **Search contacts** field alongside it at desktop widths.
3. Render saved contacts in a bordered desktop table with the columns **Name**, **Email**, **Phone**, **Medium**, and **Date requested**.
4. Keep each contact linked to its existing conversation route. Preserve a clear keyboard-focus treatment and an accessible link name; do not replace the link with pointer-only row behavior.

The **Medium** and **Date requested** values must come from the same latest contact request, ordered by request `created_at` descending with request ID as the deterministic tie-break. Date requested is the request time, not the conversation's chat-start time and not the time staff completed the follow-up.

### Search, sorting, and pagination

Search is server-side and case-insensitive across visitor name, email, and phone. Trim surrounding whitespace; an empty query behaves as no search. Apply search before counting and pagination so the count pill and pages describe the full matching result set rather than only the currently loaded ten rows.

Every displayed column has a working sort control. The default is **Date requested, descending**. Selecting Name, Email, Phone, or Medium begins ascending; selecting Date requested begins descending; selecting the active column toggles its direction. Use the conversation ID after the selected value and latest-request tie-breaks so page boundaries remain stable.

Persist state in URL query parameters: `q` for search, `sort` for the column, `dir` for direction, and the existing `page`. A new search or sort starts at page 1. Missing or invalid values fall back to the default without error. Clearing search restores the unfiltered result set. Keep the existing ten-row page size and pager behavior.

The count pill shows the total saved-contact count when unfiltered and the matching count while searching, with correct singular/plural wording. Preserve the existing **No saved contacts yet** state and add a distinct no-results state for a search with zero matches.

### Responsive and accessible presentation

Use a semantic table at desktop/tablet widths. Sort buttons must be keyboard reachable, expose the active direction through `aria-sort`, retain visible focus, and use icons rather than text glyphs or emoji for the visual chevrons. The search field needs a persistent accessible label rather than relying on its placeholder alone.

At phone widths, replace the five-column presentation with stacked contact cards whose values retain visible labels. Cards must keep the conversation link, current sort/search state, readable long email/phone values, and normal document scrolling without horizontal page overflow. Do not require a horizontally scrolling table.

## Store and compatibility requirements

Extend the internal contact-list query input to accept normalized search and sort options, and extend each returned row with the latest request timestamp paired with its medium. Apply identical filtering, ordering, counting, and tie-breaking in SQLite and PostgreSQL.

Do not add a database migration or change a public HTTP API shape. Existing contact requests remain valid without backfill. Preserve owner/staff authorization, one row per conversation, contact-request creation and completion, retention and deletion behavior, conversation links, and the rest of ticket 69's workflow.
